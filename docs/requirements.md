# 台灣政治傾向測驗 — 需求文件（草案 v0.1）

> 最後更新：2026-11-07　狀態：待確認

## 1. 定位

- 個人 side project。
- 目的是**增進自我了解**：透過問答了解自己在各政治維度上的位置，並對照台灣政黨與政治人物的立場。
- 不是投票建議工具：不告訴使用者該投給誰，也不評論哪個立場比較好。

## 2. 分階段範圍

### 第一階段（不趕 2026/11/28 選舉）
- 問卷分兩層：
  - 全國層：同意量表題，可以標記「這題對我很重要」。
  - 雙北市政層：以預算分配為主（見 §5.1），另有少數不涉及預算的政策題。
- 結果：各維度位置（雷達圖或 2D 光譜）、政黨契合度、逐題對照。
- 政黨立場資料，每個立場都附出處和證據等級。
- Claude 對答，用結構化方式修正作答（見 §6）。
- Feedback 用 Google Form，以網址參數預先填好題目、對象和立場 ID。
- 匿名上傳作答，opt-in，預設不勾選。
- 方法論頁和免責聲明。

### 第二階段
- 政治人物（目標 20 到 30 位）：
  - 雙北所有市長候選人。
  - 主要政黨各挑幾位議員候選人，各黨人數盡量平衡，以現任議員優先，挑知名度高、資料相對好找的人。
  - 指定必收：苗博雅（社民黨）、沈伯洋（民進黨）。
- 資料來源加入市議會的紀錄、訪談、辯論和社群訪談。

### 暫不做（已註記）
- 公開「多少使用者傾向某黨」這類統計。資料會先記錄下來，但不做統計也不發布。
  - 如果未來要發布，必須遵守選罷法：投票日前 10 日起不得發布選舉民調。

## 3. 政黨收錄規則

符合以下任一條件就收錄：
1. 目前在立法院有席次。
2. 最近一次立委選舉，不分區政黨票得票率 ≥ 1%。
3. 在台北市或新北市有現任議員。

收錄名單需要依中選會和立法院的資料逐一核對後確定。

## 4. 證據分級

每個立場（某對象在某題上的立場）都必須附至少一筆出處，並標示證據等級：

| 等級 | 來源 |
|---|---|
| A | 記名表決紀錄（立法院、市議會；政黨用立院黨團的表決） |
| B | 提案、連署、質詢紀錄 |
| C | 政見、黨綱、官方聲明、公開發言、**訪談、辯論、社群訪談** |
| — | 查無資料：這題不列入計算，也不推測 |

規則：
- 立場的等級取它所有出處中最高的等級。
- 呈現時把「原文」（引文、時間戳、前後語境）和「詮釋」（我們判斷這代表哪個立場）分開。
- 同一人前後講法矛盾時，以較新的為準，較早的講法也一併列出。
- 影片出處附時間戳連結。

## 5. 計分

- 作答量表分 5 級：-2（非常不同意）到 +2（非常同意），另有「不知道 / 無意見」（null，不計分）。
- 重要度：勾選「這題對我很重要」的題目權重 ×2（可調整）。
- **維度位置**：維度內各題「作答 × 題目方向」的加權平均，範圍 -2 到 +2。
- **契合度**：
  - 每題的一致度 = 1 − |使用者作答 − 對象立場| / 4。
  - 只計算雙方都有值的題目，再依重要度加權平均。
  - 一併顯示「比對題數 / 總題數」作為覆蓋率；覆蓋率太低時提示結果參考價值有限。
  - 全國層和市政層分開計分，結果也分開呈現。
- 全部在前端計算，伺服器不參與。

### 5.1 市政預算分配

- 使用者先選擇台北或新北。
- 每個項目從「維持現況」(0) 開始，可以調整 5 格：-2（大減）、-1（減）、0（維持）、+1（增）、+2（大增）。
- 第一版用**點數**計算，不換算成實際金額，實際億元留到以後再做。
- 項目分三類：
  - **支出**：增加會花點數，減少會得到點數。
  - **收入**（籌錢）：例如房屋稅（囤房稅）、大眾運輸票價、舉債。增加會得到點數，減少會花點數。
  - **結餘**：還債或留作準備金，用點數購買。
- 規則：最後餘額必須 ≥ 0 才能送出。
- 每個項目都可以設定每格的點數（`cost_per_step`），也可以對應維度和方向，用法和題目相同。
- 市政層有一個專屬維度 `city_priority`：生活照顧優先 ↔ 經濟成長優先。
  - 每個預算項目只計入一個維度。照顧類和成長類的項目只計入 `city_priority`，不重複計入全國層的 economy 軸。
- 預算題不使用重要度標記，因為調整的幅度本身就代表重視程度。
- 比對候選人時只看各項目的「方向」（增、減、不變）。證據來源：
  - 市議會審預算時的刪減、凍結提案和表決（A 級、B 級）
  - 候選人政見（C 級）
- 暫不做：「候選人政見總額是否超過預算」的比較（容易引起爭議）。

## 6. Claude 對答（結構化修正）

- 開始對話前，要明確告知作答內容和使用者輸入的文字會送到伺服器和 Anthropic。
- Claude 不能直接修改座標，只能透過 tool use 提出建議：
  1. `ask_supplementary`：從補充題庫挑題目給使用者作答。
  2. `propose_answer_change`：建議修改某題的作答，附理由。
  3. `propose_importance_change`：建議調整某題的重要度，附理由。
- 每項建議都要使用者按確認才會生效，生效後用同一套前端計分公式重新計算。
- 結果頁同時呈現「原始位置 → 修正後位置」，並列出每項修改和理由。
- Claude 的第一步通常是**解釋**：說明是哪個維度把總結果拉往某個方向，以及「左右」和「藍綠、統獨」的差別。
- 行為規範（寫進 system prompt）：
  - 只根據 App 內附有出處的資料談政黨和人物，引用時附上出處。
  - 不勸使用者投給誰，不評論哪個立場比較好。
  - 不附和使用者的自我認同：沒有作答或補充題作為根據時，不做修正。
  - 只談與本 App 相關的話題。
- 對話內容不記錄。
- 討論主題（`data/discussions.yaml`）：對答開始時可選。目前有「我的結果跟自我認同有落差」、「沉默的多數：為什麼我們不談政治？」。後者搭配不計分的反思題 X13、X14。

## 7. 隱私與記錄

- 預設在前端計算、不上傳、不綁帳號。
- 上傳作答採 opt-in，勾選框預設不勾。只記錄以下資料：
  - 作答內容與重要度標記（含補充題和 Claude 修正後的最終值）
  - 套用了哪些修正（只記結構化資料，不記文字）
  - 時間，只到小時
  - 題庫版本號
- 不記錄：IP、cookie ID、user agent、對話內容。
- 限流：IP 只放在記憶體裡做計數，幾分鐘後就丟掉，不寫入資料庫或 log。

## 8. Claude API 花費與安全

- API key 只放在後端，前端一律經由後端代理呼叫。
- 限制每次對話的回合數和 token 數，以及每個 IP 的請求頻率。
- 在 Anthropic Console 設定每月預算上限。
- 模型：預設 `claude-opus-5-5`、effort `low`，可用環境變數改成 `claude-sonnet-5-5` 降低成本。已啟用伺服器端 refusal fallback。

## 9. 技術

- 前端：React（Vite），做成靜態網站，計分邏輯也在前端。
- 後端：Python（FastAPI），只負責兩件事：Claude 代理、匿名作答記錄。
- 資料管線：Python，負責立法院 API、議會 PDF、逐字稿處理，以及 LLM 輔助擷取（最後由人工確認）。
- 資料：用 YAML 檔放在 repo 中，公開透明，詳見 `data-schema.md`。
- 部署（暫定）：
  - 前端：Vercel 或 Cloudflare Pages
  - 後端：Render 或 Fly.io
  - 作答記錄：SQLite 或 Supabase
- 介面只做繁體中文。
